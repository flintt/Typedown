# 远程存储与侧栏交互方案（WebDAV / S3 及扩展）

记录日期：2026-11-12。状态：**设计建议，待评估，尚未实现**。

本文记录“保存文件到 WebDAV、S3，以云端文件夹还是账号组织”以及后续侧栏、缓存和现有交互的讨论，并补充 SFTP、SMB、云盘官方 API 等访问方式的选择。这里只记录方案，不表示已完成远程文件功能，也不替代实现后的协议兼容性与数据安全验证。

待办入口：[远程存储设计](todo.md#remote-storage-design-2026-11-12)。

## 1. 产品组织：远程位置与存储连接

建议采用“远程位置 + 存储连接”。日常操作围绕位置和文件，不要求用户先注册 Typeleaf 账号。

| 层次 | 内容 | 职责 |
| --- | --- | --- |
| 远程位置 | “我的 NAS”“工作笔记”等显示名称，以及对应根目录 | 在侧栏浏览、新建、打开和保存文件 |
| 存储连接 | 协议、服务地址、认证配置 | 管理如何访问服务，可供多个位置复用 |
| Typeleaf 账号 | 将来自营服务、订阅或协作的身份 | 不作为连接用户自备 WebDAV / S3 的前提 |

- WebDAV 连接保存服务入口与认证信息，位置指定该服务下的根目录。
- S3 连接保存 Endpoint、Region、认证信息及必要的寻址选项；位置指定 Bucket 与 Prefix。
- 同一个连接可以对应多个位置，例如同一个 S3 服务里的 `notes/work/` 和 `notes/personal/`。
- 连接配置与密钥分开保存；界面提供测试连接、修改认证和移除连接。移除连接或侧栏位置不等于删除远端文件。
- 将来若提供 Typeleaf 自营同步，再独立设计应用账号，不把外部服务的用户名、密码、Access Key 混成一个应用登录体系。

## 2. 侧栏：扩展现有文件树

保留“文件在上、大纲在下”的现有结构，把文件区域升级为可以切换位置的文件浏览器。使用远程文件时，文件侧栏继续可用，不整体停用，也不再增加一套独立云文件面板。

示意：

```text
文件                            搜索
[ 我的 NAS / 笔记            ▾ ]  定位

▾ 项目
    产品方案.md
    会议记录.md          待上传
▾ 随笔
    十一月.md

──────────────────────────
大纲
```

顶部位置选择器沿用现有根目录选择器的位置，列出本地目录与已配置的远程位置，并提供“添加远程位置…”。选中一个位置后，下方继续显示该位置的一棵目录树。

- 本地位置、WebDAV 和 S3 用图标及显示名称区分，不要求用户在日常操作里理解 Endpoint 等配置字段。
- WebDAV 按目录展示；S3 按对象键 Prefix 映射为目录视图。界面可以一致，底层不能假设 S3 具有本地文件系统的全部目录语义。
- 展开目录时才加载该层条目，支持分页、取消、失败重试和加载提示，不在连接后递归下载或扫描整个位置。
- 切换位置时保留各位置的展开状态和滚动位置；断线不清空整个树或自动切回本地。
- 常态信息可放图标或提示中，只有待上传、冲突、失败等需要注意的状态突出显示，避免每行堆积状态文字。

## 3. 远程文件、缓存与本地副本

远程文件下载到本地后，仍然是同一篇远程文档。缓存是内部工作材料，不是侧栏里的第二个本地文件。

| 情况 | 侧栏与标签行为 |
| --- | --- |
| 仅存在远端，尚未下载 | 远程树中显示条目；打开需要连接 |
| 已下载缓存 | 仍是原条目，可表示“已缓存”；下次可以优先利用缓存并校验版本 |
| 已编辑，尚未上传 | 原条目与标签表示待上传，不另外生成可见的缓存文档 |
| 用户“下载副本” | 用户选择的本地目录产生独立文件；当前标签仍指向远端 |
| 用户“另存为本地” | 保存成功后，当前标签转为本地文档；后续保存写本地，原远端文件保留 |
| 用户“另存为远程” | 保存成功后，当前标签转为选定远程文件；后续保存回该目标 |

缓存目录不自动出现在普通文件树、最近文件、收藏或“定位当前文件”的结果中。远程文件本身可以加入最近文件和收藏，记录其位置身份，并显示来源。

“已缓存”不等于永久离线保留；若以后增加“保留离线”，需要另设明确的保留策略。缓存清理不得删除尚未上传的正文、正在编辑的必要工作副本或其恢复材料。

同一远程文件经不同入口打开，应尽可能定位到同一个文档身份和已有标签，不因使用了不同缓存路径而重复打开。

## 4. 与现有交互的对应关系

| 操作 | 建议规则 |
| --- | --- |
| 单击文件 | 沿用预览打开；网络读取在后台进行，界面可继续操作 |
| 双击文件 | 固定标签；编辑预览文档后也固定，未保存修改不得被下一次预览替换 |
| 连续点 A、B | 最后一次有效选择为准，迟到的 A 读取不能覆盖 B |
| 同时打开本地与远程文件 | 使用同一个标签栏，通过图标、提示或路径区分来源 |
| 选择侧栏位置或根目录 | 这是明确的浏览选择；后续切换标签不抢走这个根 |
| 切换标签 | 当前树包含该文件时高亮；默认不在本地与远端之间反复切根 |
| 定位当前文件 | 用户明确要求定位时，切换到文件所属位置并展开目录；绝不定位到内部缓存目录 |
| 打开本地文件／文件夹 | 保持现有系统选择框和本地语义；另设添加／打开远程位置的入口 |
| 保存、自动保存 | 保存到当前文档所属目标，与侧栏此时浏览的位置无关 |
| 关闭文档／窗口 | 依据本地修改、恢复材料和远程待写状态处理；不能把尚未上传的修改当作已保存而丢弃 |
| 应用重启 | 恢复文档身份、位置和待上传内容；网络不可用时仍能恢复本地工作，不把缓存伪装为普通本地文档 |

现有目录逻辑已经区分“用户明确打开的根”和“跟随文档得到的目录”。扩展时保留这个区别：

- 明确选择的本地或远程根保持固定。
- 尚无浏览位置时，可用首次打开文档的所属位置初始化树。
- 同一位置内、未固定根时，可沿用现有跟随策略；跨位置切换不自动抢走当前浏览位置，由位置下拉或“定位当前文件”明确切换。
- 从最近文件、收藏、标签或自动化打开文档，均使用同一份文档地址，不通过缓存文件名反推来源。

## 5. 保存、断线与冲突

第一版定位为远程文件打开与保存，不扩展为整个文件夹的双向镜像同步。

保存链路建议为：取得当前文档有效快照 → 本地可靠保留 → 按远程版本条件上传 → 成功后更新远程已保存版本。后台队列合并同一文档的连续修改，避免每次输入都上传整篇文本。

至少区分以下信息：

- 当前编辑版本。
- 已可靠保存在本地恢复材料中的版本。
- 已获服务端确认写入的远程版本。
- 当前是否在上传、冲突或失败。

界面可以表达“本地已保留”“待上传”“远程已保存”“冲突”“上传失败”。本地恢复副本写入成功，不能直接显示成远程已保存。

网络返回某次保存成功时，如果用户已经继续编辑，仍需保留后续修改的待上传状态。所有异步结果都需要核对文档身份与对应请求，不能在换标签或标签被复用后提交给另一篇文档。

打开时保留远程版本标记，保存时使用服务实际支持的条件写入：

- WebDAV 结合 ETag 与条件请求处理并发修改；锁能力按服务支持情况单独适配，不能假设所有服务器都有同样的锁行为。
- Amazon S3 可使用 `If-Match` 检查旧对象版本，创建新对象可使用 `If-None-Match`；S3 兼容服务需验证各自支持情况。
- ETag 当作服务提供的不透明版本标记，不假设它等于文件内容的 MD5。
- 缺少可靠条件写能力时，不宣称可以无冲突自动覆盖，应采用明确的限制或副本保存策略。
- 发生冲突保留双方内容，提供比较、另存副本等处理；不静默覆盖，不因上传失败回滚用户刚输入的文字。

离线时本地位置完全照常使用。远程位置保留已知目录；已缓存文件可打开，未缓存文件说明需要连接。离线编辑要先可靠保留，再表示待上传。

## 6. 搜索与远程变更发现

- 文件夹搜索以当前选定位置和根目录为范围，不偷偷搜索另一个本地目录或整个连接。
- 若第一版仅搜索缓存，必须显示“搜索已缓存文件”；结果为空不能表述成远端没有匹配。
- 远端全文搜索若需逐个读取文件，需单独设计进度、取消、流量与数量边界，不在侧栏展开时顺便启动。
- 本地仍可使用现有文件监视；远程使用提供者支持的版本检查、刷新或通知，不把 `FileSystemWatcher` 套到网络缓存上当作远端变更通知。

## 7. 右键菜单与跨位置操作

复用文件动作的目标快照和能力描述，菜单根据位置能力显示，避免每种协议复制一套完整菜单代码。

| 动作 | 远程位置的语义 |
| --- | --- |
| 打开／新窗口打开 | 使用远程文档身份；是否复用标签遵循现有规则 |
| 定位／打开文件位置 | 在所属远程位置中显示，不打开内部缓存目录 |
| 复制地址 | 复制不含凭据的远程地址；与本地“复制路径”作必要区分 |
| 下载副本 | 写入用户选择的本地目录，当前远程标签归属不变 |
| 收藏 | 收藏远程文档或目录的位置身份 |
| 新建、重命名、删除 | 按提供者能力开放；保留失败后的可恢复状态，不假设有本地回收站或原子目录改名 |
| 刷新 | 重新获取所需目录／版本；不丢弃未保存修改 |

第一版跨位置拖放默认复制，移动作为明确动作另行处理。S3 的对象／前缀操作与本地改名不能直接等同，跨服务也不能承诺原子移动。

移除侧栏位置、删除本地缓存和删除远端文件是三个不同操作，不能共用含糊的“删除”入口。

## 8. Markdown 图片与凭据

- 私有远程文档不要求文件或存储桶公开。
- 相对图片路径以远程文档所在目录为基准，通过同一连接读取与缓存，不以内部缓存文件夹重新解释路径。
- 新增图片按文档的远程目录／资源目录保存，不能只上传 `.md` 后留下仅当前设备可访问的本地图片。
- 图片和正文的多文件保存不是天然原子事务；失败时记录未完成状态，保留可重试材料，不把部分成功显示为整篇保存完成。
- 密码、Access Key、Secret Key 等进入系统安全存储；普通连接配置只保存凭据引用，导出配置默认不带密钥。
- 凭据不得进入 Markdown、复制地址、日志或普通最近文件记录。不要把受保护内容的临时访问地址当作文档的永久身份。

- [DocumentOperation](../Dev/Typedown.Core/Services/DocumentOperation.cs)：已有异步文档身份检查，应复用并按远程请求补充所需版本／世代语义。
- [S3Uploader](../Dev/Typedown.Core/Services/S3Uploader.cs)：当前是图片上传用途，内容哈希参与对象名，并返回访问地址。

建议增加的公共边界：

| 对象／模块 | 负责 | 不负责 |
| --- | --- | --- |
| StorageConnection | 协议、Endpoint、认证引用及连接配置 | 编辑器正文和界面根目录 |
| StorageLocation | ConnectionId、根目录或 Bucket／Prefix、显示名称 | 将缓存文件当作远程原文件 |
| DocumentLocation | 提供者、连接与资源键组成的文档地址 | 把密钥或临时访问 URL 塞进身份 |
| StorageProvider | 列举、读取、查询版本、条件写入及能力声明 | 各协议各写一份标签、保存状态和菜单逻辑 |
| 本地工作／恢复存储 | 缓存、恢复快照、待上传状态和清理 | 对外宣称远程已经保存成功 |

本地、WebDAV、S3 在统一接口下分别实现。继续复用现有标签、编辑器和保存编排；不要为每种协议复制 FileViewModel，也不要把远程 URL 直接塞入依赖 `Path`、`File.Exists` 的现有 `FilePath` 通路。

现有 S3 图床可复用签名、请求构建等基础能力，但文档需要稳定对象键、读取／列举／版本／条件保存，不能直接沿用“按内容哈希生成新图片名并返回公开地址”的语义。

缓存、目录元数据和上传队列都要有边界；不能为离线能力把整个远程文件夹常驻内存。连接列表、位置和会话恢复格式需要可向后读取的持久化设计。

## 10. 分阶段建议与验收

建议先明确公共存储与文档身份边界，优先接 WebDAV，再接 S3；下一种内置协议优先考虑 SFTP。SMB 并行走系统网络目录的兼容验证，云盘官方 API 按用户需求排序。各方式的边界见第 11 节；不在第一版同时承诺完整同步引擎、跨设备实时协作或远端全文索引。

第一版的闭环包括：添加连接／位置 → 按需浏览 → 打开 → 本地可靠保留 → 条件保存 → 重启恢复，并支持下载副本和另存为。提供者没有实现的文件能力须明确表达，不能显示可用菜单后静默不动作。

验收场景：

1. 本地和两个远程位置同时存在，可在同一标签栏编辑；侧栏位置与当前标签可以不同。
2. 显式选定根后切换标签不抢根；“定位当前文件”切到正确位置，缓存路径不泄漏到文件树或最近记录。
3. 连续点击不同远程文件、读写时切标签／关闭／复用标签，旧结果均不污染新文档。
4. 上传版本 N 期间继续编辑到 N+1，N 成功后 N+1 仍待上传。
5. 断网、超时、认证失效、远端被其他设备修改、对象被删除时，保留用户内容并提供可重试或副本处理。
6. 区分下载缓存、下载副本与另存为本地；同一远程文件从侧栏、收藏和最近入口打开不形成缓存副本标签。
7. 远程目录很多时按需列举，可取消旧请求；不会扫描或下载整个连接。
8. 私有图片、相对图片路径、中文／空格文件名、存量缓存与重启恢复正确，配置与日志不泄漏凭据。
9. 搜索范围标识真实；缓存命中与全远端搜索不混淆。
10. WebDAV 与选定的 S3 兼容服务分别验证条件写与不支持能力的表现，不能只用一种模拟服务代替全部兼容性结论。

后续评估点：首批支持服务及认证方式、缓存容量与离线保留、自动上传时机、冲突界面、各提供者的移动／删除能力，以及是否需要完整文件夹同步。这些不影响先明确位置、文档和缓存的职责。

## 11. 协议与服务选择补充

补充日期：2026-11-12。以下是接入建议，尚未实现，也不表示所有目标服务已经通过兼容性测试。

### 11.1 选择与接入方式

| 方式 | 适合场景 | 建议接入方式与优先级 |
| --- | --- | --- |
| WebDAV | 自备文件服务、NAS，需要按目录浏览和编辑 | 继续作为首批远程文件入口，适配目录、版本检查与条件保存 |
| S3 兼容对象存储 | 自备 Bucket、按前缀组织文档、云端存储目标 | 首批接入；沿用对象键／版本语义，不把 Prefix 当成完整本地目录语义 |
| SFTP | 自建服务器、Linux 主机、技术用户的 NAS | WebDAV、S3 之后优先考虑的内置协议；增加存储提供者，支持密码／SSH 密钥与服务端主机身份校验 |
| SMB | 家庭 NAS、公司共享目录、局域网或 VPN | 优先通过 Windows UNC 路径或映射盘访问，复用系统认证，不先在应用里另做 SMB 客户端 |
| OneDrive、Dropbox 等官方 API | 已使用这些云盘的普通用户 | 按服务分别接入，使用其授权与版本机制；若用户主要使用 OneDrive，可排到 SFTP 前 |
| NFS | 已有 NFS 环境 | 通过系统挂载使用，暂不做应用内客户端 |
| FTP／FTPS | 旧服务器兼容需求 | 有明确用户需求后再评估，不列入首批 |
| Git | Markdown 仓库与版本管理 | 单独设计本地仓库、提交、拉取和推送，不把它当作普通远程保存提供者 |

OneDrive、Dropbox 等是服务专用接入，不是一种统一文件协议。仍可挂在同一个 StorageProvider 边界下，侧栏继续显示位置和目录；不同服务的授权、文件身份、分页与变更机制由各自适配器处理。

### 11.2 保存能力不能只按协议名称推断

**SFTP：** 通过 SSH 加密传输，可使用公钥认证。需要单独设计并发修改保护：临时文件上传完成后再重命名，有助于避免直接暴露半份内容，但是否支持原子替换、覆盖行为和相关扩展需验证。它不自动等于“不会覆盖另一台设备的修改”；只先检查修改时间／大小再写入，也仍有检查与写入之间的竞态。不能直接套用 HTTP 的 ETag／If-Match 实现，更不能把网络传输加密等同于版本冲突保护。

**SMB：** 建议首先允许用户选择 `\\nas\notes` 或系统映射盘，复用系统的网络文件访问与认证。这里是兼容验证路线，不宣称现有本地流程已完整支持网络共享。重点检查断线、重连、文件监视、保存失败与恢复，以及网络文件系统上的替换语义；不能因为路径看起来像本地路径就忽略这些差异。

**云盘官方 API：** 采用服务提供的授权和版本机制。例如 Microsoft Graph 的上传会话提供 ETag 条件检查和冲突处理选项；其他服务要分别核对。用户登录微软等第三方账号，只是该存储连接的认证，不因此要求注册 Typeleaf 自有账号。临时上传／下载地址也不能成为文档的永久身份。

StorageProvider 应声明它实际支持的能力，例如条件写、重命名、服务端复制和目录操作。标签、编辑器、侧栏和保存队列复用通用规则，不能因为增加 SFTP 或云盘 API 而各复制一套。

### 11.3 rclone 作为可选桥接

高级用户可以用 rclone 将其他存储以 WebDAV 暴露，Typeleaf 复用已有 WebDAV 接入，以减少逐家接入网盘的成本。

- 它是可选扩展途径，第一版不默认要求安装 rclone，也不把捆绑进程和完整网盘管理作为前置条件。
- 桥接后的版本、条件写、重命名和错误处理能力仍需验证，不能因为入口变成 WebDAV 就自动承诺底层具有同样的数据一致性。
- 缓存、排队上传和凭据职责需要明确；若 Typeleaf 与桥接工具各有缓存，不能把桥接层尚未持久化到原服务的内容直接描述为已在原服务保存成功。

### 11.4 本轮建议顺序与补充验收

保持 WebDAV → S3 的首批计划；下一种内置协议优先 SFTP，SMB 的系统网络目录兼容验证可并行。OneDrive 等 API 根据实际用户需求调整顺序；NFS、FTP／FTPS 与 Git 不挤入首批远程文件闭环。

各类接入复用前述侧栏、文档身份、缓存和保存状态规则，并补充：

1. SFTP 的认证、主机身份、目录列举、失败保存和目标替换行为；并发改写时保留用户内容，不把检查后覆盖当成原子版本保护。
2. SMB 的 UNC／映射盘、系统认证、断网重连、文件变更通知与失败恢复；不另生成可见缓存副本。
3. 云盘授权到期／撤销、版本冲突、远端改名和身份保持；一次授权可以供多个位置使用。
4. rclone 桥接的实际保存完成边界和失败反馈；不可把桥接过程中的数据状态误报为原服务最终持久化。

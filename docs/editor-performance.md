# 编辑器性能：现状、瓶颈与决定

2026-09-25 实测。工具在 `Tools/EditorBench`：`size-curve.js`（不同长度的打开/输入成本，`--other` 可同时
量另一套内核）、`compare-editors.js`、`bench.js` + `prof-summary.js`（按环节拆解每次按键的耗时）。

**测量环境**：下面的数字都在 vm103（8 核、空闲）上量，交替跑、各三轮、取中位数，轮间波动 1~2 ms。
教训见最后一节——最初在开发机上量（4 核、有别的租户），曾经得出"节流让打开慢一倍"的错误结论。

## 改动前后

| | 30 万字符 | | 10 万字符 | |
|---|---|---|---|---|
| | 改动前 | 改动后 | 改动前 | 改动后 |
| 打开 | 4.25 s | **2.70 s** | 1.41 s | **0.93 s** |
| 按键中位数 | 100 ms | **27 ms** | 34 ms | **18 ms** |
| 按键 p90 | 157 ms | **44 ms** | 41 ms | **31 ms** |
| JS 堆 | 42 MB | 60 MB | 21 MB | 32 MB |

按键延迟降到原来的四分之一强，打开快三成七；代价是内存多四到五成（`content-visibility` 要为每个跳过的
子树记住尺寸）。

## 与 CodeMirror 6 内核的对照

对照物是 awarson2233 那个 fork 的编辑器产物（只渲染视口），同一台机器、同一测法：

| | 10 万字符 | | 30 万字符 | |
|---|---|---|---|---|
| | 我们 | 他们 | 我们 | 他们 |
| 打开 | 0.93 s | **0.19 s** | 2.67 s | **0.21 s** |
| 按键中位数 | **18.2 ms** | 18.4 ms | 27.3 ms | **16.7 ms** |
| 按键 p90 | **31.7 ms** | 31.8 ms | 43.3 ms | **29.7 ms** |
| DOM 元素 | 43,200 | 309 | 129,060 | 309 |
| JS 堆 | 32 MB | 14 MB | 60 MB | 17 MB |

**打字在十万字符上已经追平**；三十万字符仍慢一截（27 vs 17 ms），但人手打字的间隔是 100~200 ms，27 ms
落在感觉不出来的区间。**打开仍差一个量级**，而且他们完全不随长度变化（0.19 → 0.21 s），我们还是线性
（0.93 → 2.67 s）——因为我们仍把整篇建成 DOM，只是建完之后屏幕外的不排版。

## 每次按键的钱花在哪（改动前，30 万字符、7170 个块）

这一节的数字是在开发机上量的，看的是比例而不是绝对值。按键延迟平均 242 ms（含测量工具约 20 ms 开销），
包裹计时给出的 JS 部分：

| 环节 | 每次按键 |
|---|---|
| 整篇导出 Markdown（供宿主保存/比较） | 22.6 ms |
| 字数统计 | 6.8 ms |
| 大纲重算 | 4.2 ms |
| JSON 序列化（每次按键 10.9 回） | 2.3 ms |
| 输入处理本身 | 1.8 ms |
| 选区与格式 | 2.2 ms |
| **JS 合计** | **约 40 ms** |

其余不在 JS 里：CPU profile 中 `(program)` 占 82%，是浏览器在 129,060 个元素的树上做样式重算、布局与
绘制。发给宿主的 `MarkdownChange` 每次只有 9 KB（差分协议有效），不是瓶颈。

## 已做一：屏幕外的块不参与排版（`54b970a`）

给编辑器顶层块加 `content-visibility: auto`，浏览器跳过屏幕外那些块的排版与绘制。块仍在文档里——模型、
查找、滚动条、导出都不受影响。

两个踩过的坑：

1. **规则必须在首次渲染之前生效**。先全量排版、之后再加上它，浏览器要把排好的版拆开重来，比不加还慢。
   所以类在 `setMarkdown` 之前就按文档长度加上，解析完再用块数校正。
2. **类不能加在 `#ag-editor-id` 上**：渲染时 snabbdom 会 patch 这个元素，把它不认识的类删掉。加在外层的
   `#editor` 包装元素上（React 拥有、Muya 不碰）。

**三十万字符以下不启用**（一开始定的是四万，错了）：屏幕外的块没有排版，页面只能按估值算自己的高度，
而滚动条是照这个高度画的——估值偏大，滑块就偏小、一拖就跑过头。实测一个顶层块平均 51 px，原先估 120 px，
高度被高估 175%；改估 50 px 后仍有 38.6% 误差（块高分布很散，代码块和表格远高于平均），试过"按首屏实测
自动调整"反而更差（44.3%）。所以这条规则只留给"不启用就要等半分钟"的文档，三十万字符以内保持滚动条精确。
`Tools/EditorBench/scroll-height-check.js` 是量这个误差的工具。

## 已做二：整篇性的工作改为节流 + 保存前握手（`fd6499d`）

超过五万字符时，「整篇导出 + 光标换算 + 大纲」最多每 250 ms 做一次。谁要当前文本谁先 flush：编辑器侧
导出前自己 flush；宿主侧保存、另存为、分享前发 `FlushContent`、等页面回 `ContentFlushed`，最多等 500 ms，
不回就写手里已有的（宁可存旧的也不能不存）。这把"保存的一定是屏幕上的内容"从隐式假设变成显式握手。

Uno 侧同样接了（`d9e084a`）：12 万字符的文档打字后不留间隔直接 Ctrl+S，写进文件的内容带着刚敲的字。

## 决定

1. ~~整篇性的工作改为节流~~ **已做**。
2. ~~打开时不渲染首屏之外的块~~ —— 被 `content-visibility` 取代，效果更好且不动渲染流程。
3. **真正的视口渲染**（任何时候 DOM 里只有一屏）。这是剩下那条线性打开曲线的唯一解法，但等于把 Muya 的
   渲染层重做。**不做**——做到这一步就该直接比较"换 CodeMirror"。
4. **换内核**。不做。收益已经从"打字跟不上手"缩小到"开大文件多等两秒半"；而那个 fork 今年 298 次提交、
   干了大半年，至今亮色主题下菜单是黑的、字看不见。我们这两万行 Muya 里装着这些年修过的所有编辑行为。

重新评估的触发条件：日常文档经常超过三十万字符且嫌打开慢，或者决定放弃所见即所得改为源码+预览。

## 测量教训

开发机是 4 核且有别的租户，负载常在 4~8。在那上面量 250 ms 量级的差别，噪声比信号大：同一配置的打开时间
在 1.8~2.8 秒之间飘，一度让我得出"节流让打开慢一倍"的结论，重测才发现是负载。

现在的做法：**在 vm103 上量**（8 核、空闲），两种配置交替跑、各三轮、取中位数。轮间波动 1~2 ms，差别
一眼可辨。那台机器上的准备（node、Chrome、puppeteer、两份产物、对照产物）都在 `/root/tdbench`。

# 编辑器性能：现状、瓶颈与决定

2026-09-25 实测。工具在 `Tools/EditorBench`：`size-curve.js`（不同长度的打开/输入成本）、
`compare-editors.js`（与另一套内核对照）、`bench.js` + `prof-summary.js`（按环节拆解每次按键的耗时）。

## 随文档长度的变化

同一篇结构（标题+正文+列表+代码块+表格+引用），无头 Chrome，1200×900：

| 文档字符数 | 打开到渲染完 | 编辑器内 DOM 元素 | 按键中位数 | 按键 p90 | JS 堆 |
|---|---|---|---|---|---|
| 3 万 | 1.8 s | 13,068 | 40 ms | 65 ms | 24 MB |
| 10 万 | 2.7 s | 43,200 | 66 ms | 116 ms | 33 MB |
| 30 万 | 7.7 s | 129,060 | 198 ms | 356 ms | 67 MB |

DOM 元素数与字符数严格线性，按键延迟跟着它走。**十万字符是分水岭**：以内可用，以外明显难受。

作为对照，同一测法下 awarson2233 那个 fork 的 CodeMirror 6 内核（只渲染视口）：

| 文档字符数 | 打开 | DOM 元素 | 按键中位数 | 按键 p90 |
|---|---|---|---|---|
| 3 万 | 0.40 s | 309 | 24 ms | 32 ms |
| 10 万 | 0.42 s | 309 | 23 ms | 32 ms |
| 30 万 | 0.67 s | 309 | 27 ms | 36 ms |

它的曲线是平的。这是那套重构里唯一有分量的收益，与换成 WinUI 3 无关。

## 每次按键的钱花在哪（30 万字符、7170 个块）

按键延迟平均 242 ms（含测量工具约 20 ms 开销）。包裹计时给出的 JS 部分：

| 环节 | 每次按键 |
|---|---|
| 整篇导出 Markdown（供宿主保存/比较） | 22.6 ms |
| 字数统计 | 6.8 ms |
| 大纲重算 | 4.2 ms |
| JSON 序列化（每次按键 10.9 回） | 2.3 ms |
| 输入处理本身 | 1.8 ms |
| 选区与格式 | 2.2 ms |
| **JS 合计** | **约 40 ms** |

剩下的 **160~200 ms 不在 JS 里**：CPU profile 中 `(program)` 占 82%，是浏览器在 129,060 个元素的树上做
样式重算、布局与绘制。Muya 每次只改一个块（`partialRender` 的自身耗时接近零），但树太大，布局那一趟就贵。

发给宿主的 `MarkdownChange` 每次只有 9 KB（差分协议有效），这条不是瓶颈。

## 已做：屏幕外的块不参与排版（2026-09-25）

给编辑器的顶层块加 `content-visibility: auto`，浏览器就会跳过屏幕外那些块的排版与绘制。块还在文档里——
模型、查找、滚动条、导出都不受影响——省掉的只是看不见的部分的排版工作。

| 文档字符数 | 打开（前 → 后） | 按键中位数 | 按键 p90 |
|---|---|---|---|
| 3 万 | 1.84 → 1.89 s（未启用） | 42 → 39 ms | 68 → 53 ms |
| 10 万 | 2.56 → **1.93 s** | 60 → **48** ms | 90 → **64** ms |
| 30 万 | 8.03 → **4.22 s** | 186 → **75** ms | 304 → **107** ms |

两个踩过的坑，都值得记下来：

1. **这条规则必须在首次渲染之前生效**。先全量排版、之后再加上它，浏览器要把已经排好的版拆开重来，
   30 万字符那档打开反而从 8.0 秒涨到 10.4 秒。所以类在 `setMarkdown` 之前就按文档长度加上，解析完再用
   块数校正。
2. **类不能加在 `#ag-editor-id` 上**：渲染时 snabbdom 会 patch 这个元素，把它不认识的类删掉。加在外层的
   `#editor` 包装元素上（React 拥有、Muya 不碰）。

小文档不启用：四万字符（约一千个块）以下时，`content-visibility` 的记账开销超过它省下的排版时间。

## 决定

1. **整篇性的工作改为节流**——导出、字数、大纲不必每个按键都算。省约 33 ms。现在按键总共约 75 ms，
   这 33 ms 的分量从一成七变成约四成，更值得做了。**待做。**
2. ~~打开时不渲染首屏之外的块~~ —— 被上面那条 CSS 取代了，而且效果更好：不用改渲染流程，打开和打字
   一起受益。**不再需要。**
3. **真正的视口渲染**（任何时候 DOM 里只有一屏）。唯一能把 200 ms 按键延迟按下去的办法，但等于把 Muya
   的渲染层重做。**不做**——做到这一步就该直接比较"换 CodeMirror"，那是另一个量级的决定。
4. **换内核**。不做。参照物：那个 fork 今年 298 次提交、大半年，至今亮色主题下菜单是黑的、字看不见；
   而我们这两万行 Muya 里装着这些年修过的所有编辑行为。十万字符以内现状够用。

重新评估的触发条件：日常文档经常超过十万字符，或者决定放弃所见即所得改为源码+预览。

# 编辑器性能：现状、瓶颈与决定

2026-09-25 实测。工具在 `Tools/EditorBench`：`size-curve.js`（不同长度的打开/输入成本，`--other` 可同时
量另一套内核）、`compare-editors.js`、`bench.js` + `prof-summary.js`（按环节拆解每次按键的耗时）。

**测量环境**：下面的数字都在 vm103（8 核、空闲）上量，交替跑、各三轮、取中位数，轮间波动 1~2 ms。
教训见最后一节——最初在开发机上量（4 核、有别的租户），曾经得出"节流让打开慢一倍"的错误结论。

## 改动前后

| | 30 万字符 | | 10 万字符 | |
|---|---|---|---|---|
| | 改动前 | 改动后 | 改动前 | 改动后 |
| 打开 | 4.25 s | **2.70 s** | 1.41 s | **0.93 s** |
| 按键中位数 | 100 ms | **27 ms** | 34 ms | **18 ms** |
| 按键 p90 | 157 ms | **44 ms** | 41 ms | **31 ms** |
| JS 堆 | 42 MB | 60 MB | 21 MB | 32 MB |

按键延迟降到原来的四分之一强，打开快三成七；代价是内存多四到五成（`content-visibility` 要为每个跳过的
子树记住尺寸）。

## 与 CodeMirror 6 内核的对照

对照物是 awarson2233 那个 fork 的编辑器产物（只渲染视口），同一台机器、同一测法：

| | 10 万字符 | | 30 万字符 | |
|---|---|---|---|---|
| | 我们 | 他们 | 我们 | 他们 |
| 打开 | 0.93 s | **0.19 s** | 2.67 s | **0.21 s** |
| 按键中位数 | **18.2 ms** | 18.4 ms | 27.3 ms | **16.7 ms** |
| 按键 p90 | **31.7 ms** | 31.8 ms | 43.3 ms | **29.7 ms** |
| DOM 元素 | 43,200 | 309 | 129,060 | 309 |
| JS 堆 | 32 MB | 14 MB | 60 MB | 17 MB |

**打字在十万字符上已经追平**；三十万字符仍慢一截（27 vs 17 ms），但人手打字的间隔是 100~200 ms，27 ms
落在感觉不出来的区间。**打开仍差一个量级**，而且他们完全不随长度变化（0.19 → 0.21 s），我们还是线性
（0.93 → 2.67 s）——因为我们仍把整篇建成 DOM，只是建完之后屏幕外的不排版。

## 每次按键的钱花在哪（改动前，30 万字符、7170 个块）

这一节的数字是在开发机上量的，看的是比例而不是绝对值。按键延迟平均 242 ms（含测量工具约 20 ms 开销），
包裹计时给出的 JS 部分：

| 环节 | 每次按键 |
|---|---|
| 整篇导出 Markdown（供宿主保存/比较） | 22.6 ms |
| 字数统计 | 6.8 ms |
| 大纲重算 | 4.2 ms |
| JSON 序列化（每次按键 10.9 回） | 2.3 ms |
| 输入处理本身 | 1.8 ms |
| 选区与格式 | 2.2 ms |
| **JS 合计** | **约 40 ms** |

其余不在 JS 里：CPU profile 中 `(program)` 占 82%，是浏览器在 129,060 个元素的树上做样式重算、布局与
绘制。发给宿主的 `MarkdownChange` 每次只有 9 KB（差分协议有效），不是瓶颈。

## 已做一：屏幕外的块不参与排版（`54b970a`）

给编辑器顶层块加 `content-visibility: auto`，浏览器跳过屏幕外那些块的排版与绘制。块仍在文档里——模型、
查找、滚动条、导出都不受影响。

两个踩过的坑：

1. **规则必须在首次渲染之前生效**。先全量排版、之后再加上它，浏览器要把排好的版拆开重来，比不加还慢。
   所以类在 `setMarkdown` 之前就按文档长度加上，解析完再用块数校正。
2. **类不能加在 `#ag-editor-id` 上**：渲染时 snabbdom 会 patch 这个元素，把它不认识的类删掉。加在外层的
   `#editor` 包装元素上（React 拥有、Muya 不碰）。

**三十万字符以下不启用**（一开始定的是四万，错了）：屏幕外的块没有排版，页面只能按估值算自己的高度，
而滚动条是照这个高度画的——估值偏大，滑块就偏小、一拖就跑过头。实测一个顶层块平均 51 px，原先估 120 px，
高度被高估 175%；改估 50 px 后仍有 38.6% 误差（块高分布很散，代码块和表格远高于平均），试过"按首屏实测
自动调整"反而更差（44.3%）。所以这条规则只留给"不启用就要等半分钟"的文档，三十万字符以内保持滚动条精确。
`Tools/EditorBench/scroll-height-check.js` 是量这个误差的工具。

## 已做二：整篇性的工作改为节流 + 保存前握手（`fd6499d`）

超过五万字符时，「整篇导出 + 光标换算 + 大纲」最多每 250 ms 做一次。谁要当前文本谁先 flush：编辑器侧
导出前自己 flush；宿主侧保存、另存为、分享前发 `FlushContent`、等页面回 `ContentFlushed`，最多等 500 ms，
不回就写手里已有的（宁可存旧的也不能不存）。这把"保存的一定是屏幕上的内容"从隐式假设变成显式握手。

Uno 侧同样接了（`d9e084a`）：12 万字符的文档打字后不留间隔直接 Ctrl+S，写进文件的内容带着刚敲的字。

## 已做三：切换 tab 不再和旧文档做 diff（`Tools/EditorBench/tab-switch-check.js`）

一个窗口只有一个编辑器，切 tab 就是把另一篇整篇载入。30 万字符 ↔ 2 万字符来回切，改之前：

| | 改前 | 去掉 diff | 再加整篇用 HTML 串 |
|---|---|---|---|
| 切到 30 万字符那篇 | 4940 ms | 4074 ms | **2983 ms** |
| 切回 2 万字符那篇 | 1494 ms | **396 ms** | 454 ms |

两处浪费：

1. **和一篇毫无关系的文档做 diff**。渲染层每次整篇渲染都先 `toVNode` 把屏幕上的 13 万个元素读回成虚拟
   节点，再逐个 diff 掉。换文档时这个 diff 的结果必然是"全删全建"，所以整篇替换（`setMarkdown`）时直接
   把旧树丢掉，让 patch 往空元素里建。切回普通文件的 1.5 秒基本上全是这个。
2. **逐个 `createElement` 造 13 万个元素**。整篇替换时改成把虚拟节点序列化成一整串 HTML，交给解析器一次
   建完 —— 这正是 `partialRender` 每次打字对改动块做的事，每种块类型都已经走过这个序列化器。

拆解（30 万字符，改前）：解析 437 ms、建 DOM 2525 ms、光标 160 ms，其余是浏览器的样式与排版。

唯一的行为变化在数学公式的**隐藏**部分：KaTeX 同时写一棵可见的 `.katex-html` 和一棵给读屏软件的
`.katex-mathml`，后者经 HTML 解析器才是真正的 MathML（之前是一堆碰巧叫 `math` 的普通元素）。可见部分的
位置和尺寸一个像素都没动，版式基线因此重录过一次。

## 已做四：切走的文档留在内存里（用内存换卡顿）

前面三条都只是让"重建"便宜些，重建本身没去掉：一个窗口只有一个编辑器，切 tab 就是把另一篇整篇解析、
整篇建成 DOM。30 万字符是 13 万个元素，怎么省也是秒级。

现在切走时把整个编辑器元素从页面里**摘下来而不是销毁**，切回来再挂回去。摘下来的子树浏览器完全不排版，
所以代价纯粹是内存。上限：**最多 2 篇、合计不超过 80 万字符**，超了丢最久未用的。

一开始按"单篇够大才值得留"判断（门槛 10 万字符），结果 2 万字符的文件每次切回来仍要重建，实测约 0.5 秒
界面卡死。所以改成每篇都留、用**总量**封顶——判断该不该花内存，看的是总共花了多少，不是每篇够不够大。

| 30 万 ↔ 2 万字符 | 切进大文件 | 切回小文件 |
|---|---|---|
| 关掉这条（设置里可关） | 2147 ms | 604 ms |
| 开着（默认） | **493 ms** | **145 ms** |

内存：同一轮跑完、强制 GC 之后，开着 40 MB、关掉 25 MB。注意 `usedJSHeapSize` **不含 DOM 节点**，所以
真实代价比这 15 MB 大；要看真实占用得看进程 RSS。

**内存会还回去**：切走的文档三分钟内没切回就释放（每 30 秒查一次）。所以切到小文件接着干活，几分钟后
那几十兆就回来了；而来回切的场景三分钟足够，感觉不到。设置里「在内存中保留切走的文档」可以整个关掉，
关掉会立刻释放已经留着的，不是等下次切换。

数字是**主线程被占住的时长**，不是内容出现的时间。之前按"内容出现"量，得出过"切回普通文件 396 ms"这种
看着漂亮但感觉不到的结论——之后才落地的排版没算进去。`tab-switch-check.js` 现在量的是前者。

配套改了两处，都是这条的前提：

1. **设置只在真正变化时才下发。** 切换实例会让所有设置副作用重新跑，而 `setFont`、`setTextDirection`、
   `setOptions`、阅读模式那四处每个都整篇重渲染。第一版做完切换反而慢到 7.6 秒就是这个。
2. **后台实例不响应 document 级事件。** 每个实例都往 `document` 上绑了键盘的 `docHandler`、tooltip 的
   `mouseover`、浮层的 `click`，留在内存里的那份也还绑着，而且保留着被切走时的选中状态——在 A 里选中一张
   图片、切到 B、按 Backspace，会把 A 的图片删掉，屏幕上看不到任何反应，而缓存记的文本还是旧的。现在用
   `container.isConnected` 判断，只有挂在页面里的实例响应。`background-quiet-check.js` 盯着这条。
3. **渲染器改用自己的容器，不再 `document.querySelector` 找根元素。** 多个编辑器的根都叫 `ag-editor-id`，
   新建实例的构造函数会渲染一篇空文档——渲染进了还挂在页面上的那篇，把要留的文档清空了。表现是"来回切
   时间都差不多"。这是同时存在多个实例必须先解决的事。

**关掉这个开关就回到单实例。** 代码里只有两处创建实例：挂载时那一个，和切换路径里那处——后者被开关挡着。
关掉之后永远只有一个编辑器，上面这些防护全部变成空操作（只有一个实例时，它的容器就是全局查找会找到的那
个，且始终挂在页面上），行为和今天之前一行不差。其余 36 处按块 id 的全局查找之所以安全，靠的正是"后台
实例永不渲染、永不响应事件"这个前提，而不是它们本身写得安全。

## 多实例的四条规则

同时存在多个编辑器之后，下面四条是其余代码赖以成立的前提。它们**不是代码天然具备的性质**，每条都由某一处
具体实现撑着 —— 这个功能出过的每个 bug，都是其中一条被打破。清单写在 `Muya/index.tsx` 多实例那段的顶部，
新增任何会渲染、监听、上报、滚动的代码都要说明自己遵守哪一条。

| | 规则 | 由谁保证 | 检查 | 破过 |
|---|---|---|---|---|
| 1 | 只有页面里的编辑器会渲染 | `StateRender` 用自己的容器 | `tab-switch-check` | 新实例的构造函数把屏幕上的文档清空 |
| 2 | 只有页面里的编辑器响应事件 | 三处 `container.isConnected` | `background-quiet-check` | 后台文档的图片被 Backspace 删掉 |
| 3 | 换了谁显示，宿主必须被告知它现在持有什么 | `reportWhenShownRef` + 变更处理器之后的 effect | `tab-state-check` | 大纲停留在上一篇 |
| 4 | 任何东西都不许从读者手里抢走页面 | `GIVE_WAY` + 恢复路径不启动守护 | `scroll-flash-check` / `scroll-yield-check` | 拖滚动条被拽回；100 毫秒后的补位无视读者 |
| 5 | 报告不得引起被报告方再次变化 | 宿主的 `appliedCurSlug` | 暂无（需要宿主参与） | 阅读模式大纲跟随 ↔ `ScrollTo` 成环，页面自己抽动 |

第 5 条目前**没有自动检查** —— 它跨越页面与宿主两侧，而宿主是 C#，这套工具跑不起来。它是靠你报"没动它也
抽动"才发现的。

## 决定

1. ~~整篇性的工作改为节流~~ **已做**。
2. ~~打开时不渲染首屏之外的块~~ —— 被 `content-visibility` 取代，效果更好且不动渲染流程。
3. ~~每个 tab 各留一份 DOM~~ **已做**（见上一节）。当时判断"暂不做"是错的：代价只有内存，而收益是切换
   从秒级降到零点几秒。担心的 id 重复确实存在，也确实咬了一口——渲染器必须改用自己的容器。
4. **真正的视口渲染**（任何时候 DOM 里只有一屏）。这是剩下那条线性打开曲线的唯一解法，但等于把 Muya 的
   渲染层重做。**不做**——做到这一步就该直接比较"换 CodeMirror"。
5. **换内核**。不做。收益已经从"打字跟不上手"缩小到"开大文件多等两秒半"；而那个 fork 今年 298 次提交、
   干了大半年，至今亮色主题下菜单是黑的、字看不见。我们这两万行 Muya 里装着这些年修过的所有编辑行为。

重新评估的触发条件：日常文档经常超过三十万字符且嫌打开慢，或者决定放弃所见即所得改为源码+预览。

## 测量教训

开发机是 4 核且有别的租户，负载常在 4~8。在那上面量 250 ms 量级的差别，噪声比信号大：同一配置的打开时间
在 1.8~2.8 秒之间飘，一度让我得出"节流让打开慢一倍"的结论，重测才发现是负载。

现在的做法：**在 vm103 上量**（8 核、空闲），两种配置交替跑、各三轮、取中位数。轮间波动 1~2 ms，差别
一眼可辨。那台机器上的准备（node、Chrome、puppeteer、两份产物、对照产物）都在 `/root/tdbench`。

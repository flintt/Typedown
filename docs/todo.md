## 偶发启动崩溃：创建第一个窗口时（2026-10-14 发现）

在构建机（Windows 10 19045，起初误记为 Windows 11）上，测试主机启动时偶发直接退出（2026-10-14 两次，同一版本再启动则正常；Windows 10 测试机上未出现）：Microsoft.UI.Input.dll 10.0.27200.1054 中 0xc0000409（FAST_FAIL_FATAL_APP_EXIT，参数 0x8000ffff E_UNEXPECTED）。栈：App.OnLaunched → new MainWindow → DirectUI::Window 构造 → DesktopWindowImpl::OnCreate → DesktopWindowXamlSource/XamlIsland 初始化 → CXamlIslandRoot::InitializeCommon → Microsoft_UI_Input!InitializeDirectManipulationHookInProc → 主动终止。debug.log 只到 "startup: main"。崩溃时还没有执行我们的窗口代码。

| 做法 | 验证 | 成本 |
|---|---|---|
| 先查 Windows App SDK 的已知问题和更新版本（输入站点 / DirectManipulation 初始化失败）；在构建机上开 WER LocalDumps 收集完整转储（两份在构建机 CrashDumps：Typedown.exe.51804.dmp 及 19:44 Typeleaf.exe 的），对照 WinAppSDK 私有符号或提交给微软；评估启动失败时自动重试一次创建窗口是否可行 | 构建机上连续启动测试主机 50 次统计崩溃率；升级或规避后再测 | 中 |

**2026-10-16 排查**：
- 构建机应用程序日志里，新版自 10-09 起只有这两次（10-14 16:38 Typedown、19:44 Typeleaf），其余日子数百次启动都正常。
- 两次的情形不同：16:38 是 R04 杀掉宿主后立即在同一数据目录重启（转储 pid 51804 即重启的进程）；19:44 是一轮测试的第一次启动，距上一轮结束约半小时。两次前后都没有会话切换、锁屏或系统事件。
- 转储里没有第三方输入钩子 DLL（网上同类崩溃有因第三方焦点钩子引起的），只有 NVIDIA 显卡驱动和 NVIDIA 截屏组件 nvspcap64。
- Windows App SDK 2.5.1 已是最新稳定版，没有可升级的修复。
- 测试机上用 launch-loop.ps1 连续启动 100 次（50 次全新目录、50 次杀掉后立即重启）：100 次都正常出窗口，0 次崩溃。
- 下一步：等构建机空闲时在构建机上跑同样的 100 次；仍复现不出则把崩溃信息报给 Windows App SDK，不阻塞发布。

**2026-10-17 构建机上复现**：同一测试主机在构建机上连续启动 120 次，崩溃 86 次（后 20 次全崩），崩溃点相同（Microsoft.UI.Input.dll 偏移 0x26419，约 3.5–4 秒，debug.log 只到 "startup: main"）；测试机上同一构建 0 次。未锁屏；停不掉的无窗口 Typedown 进程是 WER 收集转储时的影子进程（父进程即崩溃进程），停掉其余残留后照样 20/20 崩溃，排除残留实例。网上同类报告（PowerToys、Files 等 WinUI 3 应用）有卸载第三方输入设备驱动后恢复的个例。**影响发布**：等用户确认构建机近期装过的输入相关软件、能否重启，以及试用安装版能否打开。
- 当时装在构建机上的 Typeleaf 试用包 1.3.9.16 同样崩溃（10-17 08:33、08:34），而它 06:45–07:10 启动多次都正常：构建机在 07:10 之后进入某种状态，此后新启动的 WinUI 3 进程全部崩溃，已运行的不受影响。
- 转储（cdb，公有符号）：Microsoft_UI_Input!InputSiteHwndWinRT::WndProcStatic_NoLock 第 499 行 FailFast_Unexpected（E_UNEXPECTED），在 InputSiteHwndWinRT::CreateHwnd 的 WM_NCCREATE/WM_CREATE 里，由 ContentIslandStatics::Create ← CXamlIslandRoot::InitializeCommon ← DesktopWindowXamlSource 初始化调起；进程内没有第三方 DLL。崩溃前约 3 秒停顿。
- **重启构建机后连续启动 100 次：0 次崩溃**（重启前 120 次崩 86 次）。结论：系统状态问题（疑与输入相关的会话进程有关：ctfmon、TabTip、dwm 都是 10-12 21:17 重启的，之后才出现这类崩溃），不是程序缺陷；仍值得报给 Windows App SDK。可考虑：启动时若上次在建窗口前崩溃，提示用户重启电脑（待定）。

## ✅ SF01 偶发失败：取样点落在首页的白字上（2026-10-16 查明并修好）

- 原因：新窗口现在先显示首页（2026-10-14 起）。SF01 原来只取 5 个点的亮度，其中一个点正好落在"最近文件"列表的白色文字上；前面的用例越多，列表越长，文字越容易落到那个点，列表淡入时亮度逐渐升到 189，于是判成"闪白"。窗口本身一直是深色的（PrintWindow 画出的窗口和屏幕一致，页面和各层背景都是深色）。
- 修法：SF01 改为看整个窗口有多少比例是浅色，超过四分之一才算闪白（文字只占 2–6%）。改成浅色主题跑一次，99–100% 浅色，确实会失败。
- 过程中先误判为"WebView2 自己的底色透出来"，改过 WebView 的 DefaultBackgroundColor；用新的检查对比，改与不改结果相同（都是 5–6%），已撤回，产品代码没有改动。

### ✅ 打开 / 启动恢复长文档：方案 A 已做（分支 perf/progressive-render，2026-10-18）

### 切回长文档标签页时偶发 76px 瞬时跳动（2026-10-20 发现，JU01）

全量 E2E 套件跑多次（w10、hp 各自独立跑）都稳定复现：JU01"切回标签页"子场景里，文字刚变得可读之后约 50ms 内，有 1-2 帧相对最终画面偏移 76px，随后自己纠正，最终落点是对的（TopBlockScript 前后一致）。单独跑 JU01（或跟它紧邻的用例一起跑）从未复现，必须是"先跑过 S0 到 JU01 之间这 29 个用例"才会触发（已用这个 30 用例的前缀稳定复现，不需要跑完整 130+ 用例套件，省时间）。

- 已排除：不是"新开窗口"那条子场景的问题（那条窗口几何振荡幅度其实更大，但从未触发跳动检测，因为窗口刚打开时页面是空白的，振荡发生在文字可读之前）。
- 已排除：不是 `estimateRest` 的 100ms 节流频率——把切回标签页头 500ms 内的节流收紧到 30ms（b01fb4a2 的改动，已撤销）后，w10、hp 上该跳动仍然 100% 复现，幅度、时间点几乎不变。
- 机制：切回标签页走的是"锚点恢复"路径（`Muya/index.tsx` 的 `settleScroll`，`keepScroll && at && leaf` 分支），这条路径上有两套独立的滚动纠正同时在跑——渐进渲染自己的逐片补偿（`render/index.js` 的 `keepInPlace`，按渲染切片节奏）和滚动恢复的持续按住补偿（`settleScroll` 的 `hold()`，按动画帧节奏，每帧用锚点元素重新算一次目标位置）。两者测量不同的元素、按不同节奏触发，文字刚可读的那一两帧里偶尔会短暂不一致，表现为这个小跳动。"新开窗口"用的是同一套锚点逻辑，但窗口创建本身慢（~800ms+），两套机制有更多时间提前收敛，所以不触发。
- 决定：先不继续动这两套机制（结构性改动，要让它们不打架需要仔细验证，不确定值不值得现在做），记录为已知的轻微瞬时问题——76px、不到 50ms、自纠正、不影响最终落点。以后要修的话，方向是让其中一套机制在另一套还在收敛时让步，而不是再调节流频率。

### 一次编辑后整篇格式被规范化，脚注搬到文末（2026-10-18，用户反馈；非 bug，待决定要不要改）

showcase.md 这类含原始 HTML、GFM 扩展语法的文档，只要有任何编辑（哪怕一次回车），页面就要把整篇导出一次（Muya 的 AST 往返不是逐字节保真的），表格分隔线、空行会被规范化，**脚注定义会被搬到文档末尾**，不论原来写在哪。用一行版本管理/diff 工具看，这会显示成几乎整篇都变了（本例：1089/1152 行不同），即使实际内容没丢。已用 showcase-check.js 在改动前后分别验证：开关"分段渲染"对这个现象没有影响，纯粹是既有的导出规范化行为；该测试本来就把这类格式差异当"展示但不算失败"，只有真的丢词才算失败。

### sequence 时序图偶发渲染超时（2026-10-18 发现，perf/progressive-render）

长文档背景补全阶段画 `sequence` 代码块（js-sequence-diagrams，Snap.svg）时，字体加载等待（webfontloader）偶尔不触发 `active`/`inactive` 任何一个回调，Promise 永不 settle。已加超时（8s）+ 最多 3 次重试（0133e983），showcase-check.js 多次测试里偶尔（约 1/4 次）仍然超时；同一问题（flowchart.js）已经另外查明是我自己加的超时包装对同步返回值调用了 `.then()`，已修好且稳定。

## ✅ 标签加载期间按键丢失（2026-10-14 发现；2026-10-17 已做）

**做法（已做）**：新建或切换标签一开始，宿主先发 HoldInput，页面把键盘移到页面内一个隐藏输入框，期间的字母、回车、输入法上屏都存在那里；每个 LoadFile 带最新的 hold 编号，页面拿到那个文档并发出 FileLoaded 后，把暂存文字作为读者的编辑插到光标处，再把键盘还给编辑器。两次快速切换之间打的字归当时那个标签：下一次切换前的 flush 会等它进去（新建标签前也先 flush）。阅读模式、源码模式的 Vim 不暂存；组字中的输入法先打完。单元测试 inputHold.test.ts；端到端 TL01（切到约 30 万字的长文档，关掉暂存时失败）。
- 单击标签、"+" 按钮会把键盘拿到标签栏上，界面线程忙于长文档时要 300–600 ms 才交回网页视图，期间的字符丢失（网页只收到按下）：标签和 "+" 改为点击时不拿焦点（AllowFocusOnInteraction=False）；新建标签后键盘已在网页视图时不再移出移入（FocusEditorInPlace），移出移入后输入法会丢掉紧接着的字符。落到标签栏或编辑器控件上的字符也转给页面。TL01（含单击长文档标签、长文档后点 "+"）开着暂存 3/3 通过，关掉暂存 2/2 失败。
- 留下的缺口：快捷键由宿主处理，页面要等宿主转来 HoldInput；按下快捷键后几毫秒内（工具连发）的键仍可能落在旧文档。
- 另一个问题（未做）：切到标题极多的文档（测试中 3000 个标题）时，大纲在界面线程上建树约 0.5 秒，期间网页视图拿不到键盘，单击标签后立即打的字可能丢失（键按下事件晚到、字符丢失）。做法：大纲分批建或延后建；验证：TL01 的长文档改回 3000 个标题后通过。
- 测试注意：测试机开着中文输入法（中文模式），用虚拟键打字母时回车被输入法拿去上屏；TL01 的字母用字符输入。


新建标签（Ctrl+N、"+"、文件 → 首页、⌂、自动化接口 document.create）和切换标签（单击、Ctrl+Tab）时，宿主先换掉当前标签，编辑器页面要过一会儿才收到新文档；这期间按的键落在页面里还显示着的旧文档上，随后被丢掉：
- `TabsViewModel.BeginNewTab()` 只改宿主状态，页面仍显示旧文档、键盘还在页面里；`FileViewModel.NewFileFun()` 可能先等磁盘（`CheckBackup`），之后才设空白文本并 `EditorViewModel.PostLoadFile()`（LoadId+1，发 LoadFile），最后 `FocusEditor()`。`SwitchTo()` → `Restore()` 同理。
- 这段时间的按键：页面的 MarkdownChange 若在 PostLoadFile 之后到达，按旧 LoadId 被当作过期丢掉（键既不在旧文档也不在新文档）；若在等磁盘期间到达，LoadId 还对得上，旧文本加按键被写进新标签的状态，随即被空白文本覆盖（新标签短暂显示旧内容、像未保存）；LoadFile 已发出但页面未处理时的按键也会被加载清掉。
- 现在的绕法：用例 K05、HP05 在新建或切换后等 1.5 秒再打字。

- **形式**：盖在编辑区上方的原生界面，不放进编辑器网页。标签本身照旧是空白文档：从首页打开文件就在这个标签里打开；开始打字、粘贴、拖放、自动化接口写入、点"新建空白文档"时首页收起，键盘回到编辑器。
- **内容（从上到下）**：新建 / 打开文件 / 打开文件夹；收藏；最近文件（文件名、所在目录、修改时间，可右键移除、可收藏）；最近文件夹；底部一行快捷键提示和去设置的链接。不放文件内容预览或缩略图（要读文件，慢，也有隐私问题）。
- **设置位置**：设置 → 常规 → 应用 → "启动时"折叠项，在"文件 / 文件夹"两行下面加"空白标签显示首页"（默认开）和"新建标签也显示首页"（默认关）。理由：这里就是决定"打开程序看到什么"的地方；不放 视图 → 布局（会和"始终显示标签栏"混在一起，而首页不只管启动）；不做成 FileStartupAction 的第四个选项（首页还管关掉最后一个标签和打开上次失败，且会动 SE01 已验证的枚举）。自动化接口的外部设置先不加这两项。
- **风险**：首页收起后的焦点（K05、K06、FO01，要在有窗口管理器的桌面上验证）；草稿恢复对话框出现在首页上面；最近列表要异步加载，不能拖慢启动（#16 的日志数字核对）。

**端到端用例**：
- RC01 打开 A、B 两个文件夹后，打开最近 → 文件夹 依次列出 B、A，点击切换文件树根目录。
- RC02 最近列表里的文件被删掉后显示为灰色、可移除；"清除最近文件"不动文件夹记录。
- RC03 关掉"记录最近打开的文件"后打开文件，列表不变；"清除最近记录"把文件和文件夹记录都清空。
- FV01 收藏一个文件和一个文件夹，重启后收藏分组和首页都还在；在文件树里改名后收藏跟着更新。
- FN01 上一级、下拉里的上级路径能切换根目录；"设为根目录"生效；已打开的标签不受影响。
- HP01 默认设置启动看到首页；点最近文件后在同一个标签打开，首页消失。
- HP02 Ctrl+N 和"+"不出现首页，按键直接进文档（K05 保持通过）；打开"新建标签也显示首页"后出现。
- HP03 关掉最后一个标签出现首页；会话里的文件都不在时也出现首页；开关关闭时是空白文档。
- HP04 有文件打开时，文件 → 首页、"⌂"按钮、快捷键都能回到首页，已打开的文件不受影响；自动化接口写入首页所在标签后首页收起，内容正确。
- HP05 首页收起后按键进入编辑器（有窗口管理器的桌面）。
- SE01 扩展：两个首页开关写进设置文件。

**建议顺序**：1 → 2 → 3 → 4 → 5；6 可选，单独排期。
**不建议**：侧栏里铺开的完整面包屑和后退/前进（侧栏太窄，收益低）；首页做成编辑器网页里的 HTML；用数据库表存收藏；首页显示文件内容预览；自动删除找不到的最近或收藏条目；首页做成固定不能关的标签或侧栏的一页。
与已有条目的关系：R08（最近访问去重和初始化，已做，是基础）；#17 单击预览（收藏分组单击行为要一致）；#23 大纲和文件树同时显示（同一块侧栏布局）；#16 启动耗时。

## Shazao Release 对照与后续功能设想（2026-10-16）

**记录者：OpenAI Codex（AI 助手）。** 本节是基于当前工作分支代码和公开 Release 说明提出的分析建议，尚未实施或排期。Shazao 的功能以其作者发布的说明为准，未安装实测；其 [v0.6.6](https://github.com/yakoye/Shazao-markdown/releases/tag/v0.6.6) 仍说明中文输入法、多 DPI 和设备差异需要独立验收。

**基线**：本分支已有首页、最近记录、收藏、文件夹导航、文件夹全文搜索、网页 HTML 表格粘贴、每篇文档的光标与纵向滚动位置。Typeleaf 扩展已有写作时间线、目标、Word 模板导出和可与当前正文逐行比较的 Pro 版本历史。评估新功能时按这些现状增量设计，不把已有能力重新列为缺失。

**先补现有功能的可靠性**：

1. 新建／切换标签及收起首页后立即输入可能丢字，见上文“标签加载期间按键丢失”。验收应去掉 K05、HP05 的 1.5 秒等待，连续输入、回车和中文输入法上屏都进入目标文档，旧文档不变。
2. `FileViewModel.SaveCore` 调用 `EditorViewModel.FlushContentAsync()` 后未检查返回值；超时时应避免把旧缓冲区当作最新正文保存。先以可控超时和切标签交错测试确认行为，再并入 R01／R03 的保存快照方案。
3. 深色编辑区浅色闪帧（SF01）查明是测试取样点落在首页白字上，改为测窗口浅色占比后，含 WV01 浏览器进程恢复的组合也通过；`00b09ce1` 的 WebView2 背景改动经对比无差别，已撤回。偶发原生启动崩溃按上文记录继续取证。
